# 旅行规划评分规则

用同一套规则独立评估 baseline 和完整 Agent。先报告请求成功率、格式通过率和生成行程的比例，再比较质量。请求失败与格式错误单列；不能把它们当作已通过的行程。

## 必要指标

| 指标 | 1 分 | 0 分 | N/A |
| --- | --- | --- | --- |
| 目的地正确 | 行程所在目的地与用户最终确认的目的地一致 | 行程排到了错误的目的地 | 用户未指定目的地，或未生成行程 |
| 抵达与离开时间区间 | 最早安排不早于抵达时间，最晚安排不晚于离开时间；只提供一端时只检查该端 | 任一已知时间边界被违反 | 没有已知边界、输入本身有冲突，或行程缺少判断所需的日期或时间 |
| 必游景点全覆盖 | 行程包含用户最终指定的全部必游景点 | 漏掉至少一个必游景点 | 用户未指定必游景点，或未生成行程 |
| 到达时景点开放 | 所有安排到达的景点在对应日期及到达时刻开放。当前行程用活动的 `start_time` 作为到达时刻 | 至少一个景点在到达时未开放，包括闭馆日、开门前及闭馆时或之后 | 未生成行程，或因日期、到达时刻或开放时间缺失而无法确认全部，且尚未发现明确违规 |
| 指定住宿地点正确 | 抵达日可不从酒店出发，离开日可不返回酒店；其余每天需从酒店出发并返回酒店 | 明确违反需要从酒店出发或返回酒店的条件 | 用户未指定具体住宿地点，或未生成行程 |

按最后一轮后的 `expected` 判分。到离时间以用户提供的抵达和离开边界分别计数，必游景点按去重后的必游景点数计数，景点开放按行程中的活动次数计数，指定住宿按一个住宿要求计数。每项以「通过数 / 应检查数」展示；无法判定的项目仍在分母中，并单独标注数量、具体项目和原因，不能视为未通过。没有适用项目时记 `N/A`。只有日期时按日期比较，不补造具体时刻；明确撤销「必游」不等于禁止访问。

自动评分时，`expected` 取自案例标注，模型只收到对话与资料。目的地通过行程景点所属城市判断，库外地点可能导致 N/A；到离时间检查活动起止时刻，返程是否及时由路线可行性检查，未计入这一单独指标；开放时间只检查到达时刻和常规星期营业时间；住宿按每天第一项活动或其出发地点及最后一项活动判断；抵达日不要求酒店出发，离开日不要求返回酒店；日期或指定酒店无法匹配时可能记 N/A。酒店活动不计入景点开放、偏好或重复率。任一项存在明确违规时计 0，信息不足且没有明确违规则记 N/A。

## 偏好指标

指标 1 类型偏好按最终的 `preferred_attraction_types` 分别计算。对每个标签，将带有该标签的景点的实际安排时长相加，再除以全程景点参观时长。多标签景点的时长分别计入各匹配标签，分母只计一次；交通和休息不计入。每个标签的时长占比达到 60% 即达标。逐例报告各标签占比与标签达标率（达标标签数除以该案例的偏好标签数）。汇总时，用所有可评分案例的达标标签数除以偏好标签总数。未表达偏好，或缺少可计算的行程数据，记为 `N/A`，并单独报告有偏好案例的可评分数量。

指标 2 衡量**舒适度偏好**。每天分开统计两项：**步行时间**包括纯步行和公共交通中的步行接驳；**总交通时间**只计非步行部分，例如乘车、候车和换乘等待。如果公共交通接口只返回包含步行的总耗时、无法拆分，不能把整个耗时计入非步行交通，该项标为 `N/A`。

首版每日上限分别为轻松 45/90 分钟、适宜 75/120 分钟、充实 105/150 分钟，前者为步行，后者为非步行交通。两项均不超过上限才算当天达标，报告可评分天的达标率。仅当案例明确给出同一天的抵达和离开时间，且间隔不超过 6 小时时，将上限减半。其他情形沿用全天阈值。没有舒适度偏好时仍展示可计算的耗时，达标率记为 N/A。

指标 3 衡量顺路达标率：逐天按照模型选择的步行或公共交通方式，检查相邻活动之间的可用时间能否覆盖离线路线耗时；明确不可行记 0。可行时，将模型耗时与相同地点、起终点、允许方式和时间约束下的参考最优耗时比较，额外耗时不超过最优耗时的 15% 或 5 分钟（取较大者）记 1，否则记 0。缺少必要路线或时间数据、没有可行参考解时该日记 N/A；分母为全部已生成行程天数，日志单独记录未判定天数。

首版按天枚举同一组景点的访问顺序。对固定的交通耗时数据，排除违反时间约束的方案，再取可行方案中总转场耗时最少的一条作为参考。

当前实现的边界：只计算模型明确输出的路线，不默认补充返程；非离开日未安排返回指定住宿时，交通负担记 N/A。酒店作为起点或终点时固定该端点，未指定住宿端点时枚举景点顺序。参考路线逐段使用当天已出现的交通方式中耗时最短者；开放时间或路线数据不足时记 N/A。路线数据为固定时间的估计。

枚举仅在生成结束后的评分阶段执行，评分器不会将参考路线或评分反馈给 Baseline，也不会修改模型的输出。评分结果展示模型原有的景点顺序及可行参考顺序。

路线工具约定返回三个耗时字段，单位均为秒：

| 字段 | 名称 |
| --- | --- |
| `walk_only_seconds` | 全程步行耗时 |
| `transit_total_seconds` | 公共交通方案全程耗时（含步行接驳） |
| `transit_walk_seconds` | 公共交通方案内的步行耗时 |

选择公共交通时，舒适度偏好的非步行交通耗时为 `transit_total_seconds - transit_walk_seconds`，顺路程度直接使用 `transit_total_seconds`。查不到的值保留 `null`。

## 景点重复率

景点重复率是全程重复出现的不同景点数除以全程去重后的景点数。某个景点无论出现两次还是更多次，分子都只加一。没有可评分行程时记为 N/A。该指标按地点 ID 统计所有重复，并列出景点及出现次数，不自动判断重复是否由用户要求或是否合理。

## 诊断项与评分脚本

多轮修改、事实有据及应答是否合适用于失败分析。多轮修改检查最新要求是否落实、其他有效条件是否保留；应答是否合适检查澄清或范围说明是否必要。

区分计划和事实：「建议预留 45 分钟」是安排；「官网建议 45 分钟」需要来源。票价等缺失字段不作为 0 处理。结构化事实的自动检查筛出库外景点 ID 和无依据交通耗时。对使用路线数据的 ImprovementV2（含历史 baseline-v3），非空交通分钟数与对应本地数据比较，允许一分钟误差；baseline-v2 和无路线数据的 baseline-no-routes-v1 保留原先要求空值的规则。`message`、`note`、`assumptions` 中的事实仍需人工核对。

汇总时，分别累计各指标的通过项目数和应检查项目数，并报告未判定项目数及没有适用项目或结果的案例数。逐案例结果列出项目、结果和判断依据。

在项目目录离线运行：

```sh
python evaluation/score_baseline.py results/baseline/运行目录/DEV-01/result.jsonl
python evaluation/score_baseline.py results/baseline/运行目录
```

当前脚本自动统计五项必要指标、类型偏好和可计算的两项路线指标，并逐项报告分数、证据或 N/A 原因。脚本不调用模型，也不修正输出。每次运行案例后自动生成 `result.score.md`，并在终端输出评分。

每个案例的 `result.score.json` 和运行目录内的 `scores.json` 保存案例编号及各项最终值和 N/A 原因。各指标以「数值」和「原因」子字段表示，必要指标、景点类型偏好、舒适度偏好和重复率的数值为「分子/分母」；顺路达标率以「达标天数/生成行程天数」表示。无法完整判定的必要指标、没有偏好或不可比较的值为 JSON `null`。逐项证据、重复景点清单、未知原因和逐日明细保留在评分日志中。可对已有结果执行 `python evaluation/score_baseline.py 结果路径 --json-output 评分.json`，输出文件必须不存在。
