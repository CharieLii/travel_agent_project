# COMP5511 旅行规划 Agent 开发计划

**计划日期：2026 年 11 月 9 日（香港时间）**

先完成一个能在终端运行的香港一日游 Agent：**生成行程 → 检查开放时间和交通衔接 → 修正行程 → 根据用户的新要求再次调整**。跑通后，再扩展到多日、更多城市和更大的测试集。

## 项目要求与范围

- **课程要求**：可运行的实现、可衡量的评估、课堂展示，以及可复现主要结果的源码和 README。最终报告使用英文。
- **Proposal 计划**：使用 LangChain 和 LangGraph，覆盖三个城市、约 100 个景点和 20 个住宿起点，准备 30 条开发案例和 60 条独立测试案例。
- **首版范围**：香港、约 8–12 个景点、1 个住宿起点、命令行交互。项目标题和核心方法保持一致，最终报告如实说明实际实现与评测范围。

## 开发顺序与验收标准

| 步骤 | 实现内容 | 验收标准 |
| --- | --- | --- |
| 1. 数据与检查器 | 整理地点 ID、开放时间、游览时长、活动标签和演示用交通时间。保留来源，标注估计值。用 Python 检查开放时间和交通衔接。 | 给检查器一份有问题的行程，它能指出具体违规；修正后的行程能通过。 |
| 2. 接入大模型 | 用 LangChain 接入可用的模型。提供候选地点和交通资料，让模型输出含地点 ID 和起止时间的结构化行程。 | 终端输入需求后，模型返回可供检查器读取的行程。保留单次生成路径作为基线。 |
| 3. 串起 Agent 工作流 | 用 LangGraph 管理需求提取、地点检索、生成、检查和修正。把具体违规反馈给模型，最多修正两次。 | 能看到发现的问题和修正结果；若仍无法通过，明确说明未解决的冲突。 |
| 4. 支持多轮更新 | 保存住宿、到离时间、兴趣、必去地点和当前行程。新消息只更新有关条件，再规划受影响的部分。 | 扩展到多日后，用户说「第二天下午安排轻松一点，但保留艺术馆」，系统能修改第二天，并保留艺术馆及其他有效要求。 |

模型负责理解需求和生成行程，Python 负责核对事实和时间，LangGraph 负责决定下一步。首版由模型安排景点顺序，无需另写路线优化算法。儿童或长者同行可触发澄清，例如是否需要午后休息；系统根据确认后的需求安排活动。

## 实验与评估

第一轮实验回答：**在模型、用户需求、地点与交通资料相同的情况下，加入自动检查与修正是否提高行程可行率？**

- **基线**：同一模型单次生成行程。
- **完整 Agent**：使用同一模型生成行程，再根据检查结果修正。两种方法的最终输出用同一套检查规则评分。
- **案例**：先固定 8–12 条未用于调试的案例，标为初步实验。单城流程稳定后再增加城市和场景；开发案例与最终测试案例分开。
- **指标**：在本身有可行解的案例上统计行程可行率，同时记录需求满足率、多轮修改成功率和响应时间。保留两种方法的原始输出、检查结果和耗时，供 slides 和报告使用。

## 第一个编码任务

实现 `validate_itinerary()`。准备两个景点，让前一个活动在 11:00 结束，后一个在 11:10 开始，而交通需要 30 分钟。检查器应返回「转场缺少 20 分钟」。把后一个活动改到 11:30，并确保它仍在开放时间内，检查器应判定通过。这一步不需要 API key 或 LangGraph。
